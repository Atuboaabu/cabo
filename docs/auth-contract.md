> **Phase 5-0 最终整合稿 / 业务契约已冻结**

## 0. 契约优先级与原有规范

1. `docs/game-rules.md` 是玩法 Source of Truth；`docs/domain-model.md`、`docs/state-machine.md`、`docs/player-views.md` 和 `docs/phase4-consolidated-contract.md` 约束游戏业务。认证层不得改变这些已冻结的业务效果。
2. **本文件只规定账号、身份及身份导致的访问限制**。若涉及 Room/Turn/Game/Result 的已确认状态，则适用原 Phase 4 契约；认证规则只能控制能否访问，不能替换游戏裁决。
3. 后续显式修订才覆盖相应条款。**AUTH-5 原 B（未验证邮箱允许注册并参与）已由 AUTH-5-R1「注册前必须完成邮箱验证码证明」替代**；历史 AUTH-I021、AUTH-I038、AUTH-I044 及原有关于未验证正式账号的表述仅作为旧版本记录，不再对新注册生效。AUTH-16 的原“注销立即/延迟执行”二选一草案已被后续明确确认的**Game Playing 禁普通账号设置和注销**规则替代；AUTH-15-Lobby A 进一步规定 Leave 与注销是独立的正式操作。
4. **AUTH-18 原 A（展示名允许重复）由 AUTH-18-R1 替代**：注册名就是游戏展示名，全局唯一、允许修改但新名称仍须唯一。历史 AUTH-I112 的「允许重复」已失效；AUTH-I113 关于 Player Identity 授权的规定仍有效。当前不新增 CM 决策，不打开已冻结的 Phase 4 语义。任何实现阶段发现的矛盾须先报告和确认。

## 1. 身份与授权边界（AUTH-1、AUTH-3、AUTH-4、AUTH-19）

| 概念 | 含义 | 不得等同于 |
|---|---|---|
| **Account ID** | 稳定的认证主体；负责注册信息、凭证、会话和账号控制 | Player ID、展示名、Room Member |
| **Authenticated Session** | 特定设备或浏览器当前已通过认证、未失效的会话资格 | Game Participant / 当前有效 Game Connection |
| **Room Member / Player ID** | 服务端可信关联的业务参与身份；Room 成员资格与 Game 参与资格分开核验 | Account ID、客户端自报 Player ID、显示名 |
| **Game Participant** | Start 时冻结的 Player 及固定座次，不因掉线/重新登录而改变 | 当前在线状态、当前 Room 新成员 |
| **Active Game Connection** | 每 Player 最多一个当前有效实时连接，依 CM-68 正式接管 | 多设备登录会话本身 |

- Room Create/Join 必须由当前合法认证的账号发起；认证成功只意味着有资格发起检查，不自动授予 Room、Host、Game 或秘密权限。
- **同一 Account 同时最多一个有效 Room Member 身份**，包括跨浏览器、跨设备和并发 Create/Join；不能重复占席。已在 Room A 时不能 Create/Join Room B，须先完成合法 Leave。返回 A 应恢复旧成员身份，不新建席位。
- 一个账号在同一 Room/Game 不得拥有两个不同 Player 席位；跨 Game 或 Room 的身份关系仍需服务端校验，不能推定各处 Player ID 相等或一定不同。
- Room Closed 或成员正式移除后，不再占用当前成员资格；Room/ Game 旧历史身份和已确认结果不被删除或重分配。
- 允许同一 Account 的多个 Authenticated Session 并存；**每 Player 的当前游戏实时连接仅一条**。新连接接管不自动注销旧设备的账号会话，却立即剥夺旧连接提交新的游戏 Command 或接收新私人结果的资格。
- 所有受保护请求独立核对：当前认证、可信 Account–Player 绑定、目标 Room/Game 身份、业务状态、必要的当前连接资格和私人授权；仅提供 ID 或登录态都不够。

## 2. 注册、邮箱唯一性和邮箱验证码（AUTH-1、AUTH-2、AUTH-5-R1、AUTH-7 A、AUTH-8 A）

1. MVP 使用**注册名 + 邮箱 + 密码**注册，使用邮箱 + 密码登录；注册名即游戏展示名，遵守 AUTH-18-R1 全局唯一约束。不允许游客创建或加入 Room。**完成注册前必须验证邮箱控制权**：提交符合格式的邮箱和密码 → 请求向该邮箱发送一次性数字验证码 → 用户填写验证码 → 服务端校验成功并完成注册。仅检查邮箱格式或邮件发送成功不等于邮箱已验证。
2. **未完成邮箱验证码验证的注册申请不是正式 Account**，不得登录，也不得创建、加入 Room。注册正式成功时，邮箱状态即 Verified；之后合法登录才可按 Room 原有条件参与游戏。不能再按旧 AUTH-5 B 允许未验证邮箱正式账号直接加入。
3. 一个**规范化邮箱**在所有正式账号中最多归属一个账号；注册名/展示名也须按统一、明确的名称比较规则全局唯一。注册申请中的暂时验证流程不得冒充正式账号或永久占用邮箱；验证码正式消费和账号注册提交时必须再次验证全局唯一性，并保证同邮箱并发注册最终最多成立一个账号。规范化规则统一；不擅自合并所有提供商的点号或 `+` 别名。
4. 注册验证码由服务端校验，绑定**特定规范化邮箱、注册用途、具体注册验证上下文、有限有效期**，且一次有效；过期、错误、已消费、已撤销或已被替代的验证码不能完成注册。重发应使旧码按正式规则失效；成功消费不得创建第二个 Account。验证码不得在日志、公开 View 或普通成功响应中回显。
5. 邮件发送失败、验证码错误、过期、重试次数过多、取消注册和中途关闭页面，均不得创建可登录的正式账号。注册页面可以清楚提示用户检查邮箱、重新发送验证码及返回修改邮箱；服务端必须限制发送频率、校验尝试、并发验证及滥用行为。
6. 邮箱验证码证明的是**该邮箱在本次注册用途下的控制权**，不代表对任何现存账号的管理权。现有账号的改绑邮箱沿用 AUTH-11：须同时具备原账号的独立再认证和新邮箱验证；注册验证码不得用于登录、密码重置或更换其他账号的邮箱。
7. **AUTH-8 A 保留安全边界**：未验证邮箱不得用于邮箱密码恢复。新注册账号在注册成功时已 Verified；未完成注册的邮箱没有可恢复的正式账号密码。若历史/外部迁移原因存在旧 Unverified 账号，不得仅因该邮箱收到注册验证码而自动将其升级、接管或允许重置密码。
8. 注册、登录、验证码发送及恢复入口不得在非授权场景披露不必要的 Account ID、Game 历史、账号验证状态等信息。不得向未完成独立认证者泄漏其他账号的存在细节；可以向用户提供安全一致的邮箱占用或无法完成注册的提示。

### 历史未验证账号与邮箱占用争议（AUTH-10 A）

- **新流程不允许创建未验证邮箱的正式账号。** 以下规则只适用于此前已存在或外部迁移的 Unverified 账号（如果实际存在）；不能用待验证注册申请人为制造长期邮箱抢注。历史未验证邮箱占用**不因一段时间过去而自动释放**。
- 合法现有账号控制者可通过正式邮箱变更释放旧标识；或者通过独立、授权、可追溯的人工争议处理，**仅释放邮箱占用关系**。
- 不因邮箱释放把原 Account、Player、Game 历史或私人结果交给邮箱持有人；不自动修改已生效 Room/Game/Command 事实。争议处置不得披露其他人的个人资料和秘密。
- 邮箱占用释放后旧账号可能需另行建立合法登录/联系渠道；这不构成准许自动绑定陌生邮箱或迁移身份的权限。

## 3. 密码、恢复、主动修改及安全通知（AUTH-2、AUTH-6 A、AUTH-8 A、AUTH-13 A、AUTH-14 A、AUTH-17 A）

- 密码不得明文保存、记录、回传或通过可见错误泄漏；必须使用适当的专用密码哈希与验证机制。登录失败不等于 Game Action 或 Room 成员变化。
- **忘记密码**：仅 Verified 邮箱可作为该账号的邮箱恢复依据；恢复凭据须限定账号、用途及有效期限，合法独立验证成功后才能正式重置。不能仅提交邮箱直接改变密码。
- **主动修改密码**：必须重新证明当前账号控制权；不能仅依客户端存在登录 UI 就断言已完成再认证。
- 两种密码变更成功后都使**旧密码及该账号全部既有会话和续期资格失效**，须以新凭证重新登录；已经正式 Accepted/Rejected 的 Game Command 不回滚。
- 普通 **Logout** 仅撤销本次 Authenticated Session，不影响同账号其他未撤销会话；退出不自动执行 Room Leave。
- 登录、注册、邮箱验证和恢复入口采用分层限流、滥用防护和安全一致的公开反馈；正常错误密码不应被攻击者利用为永久锁死他人账号的通道。频率防护不是跳过实际认证的许可。
- 密码修改、密码重置、邮箱变更、账号注销等关键操作尽力发送**单独的安全通知**（邮箱变更应通知原邮箱）。通知不含密码、Session Token、完整恢复凭据、私人牌值；通知送达、阅读、迟到或重复不影响原操作正式结局，也不重复触发修改。
- 恢复所需的验证邮件与**操作完成后的安全通知**是不同用途，不得混为具有相同授权能力的消息。

## 4. 修改邮箱（AUTH-11 A）

1. 重新证明账号控制资格，并验证**新邮箱**所有权；未全部通过前，旧邮箱关系保持正式有效。
2. 凭据绑定目标账号、新邮箱、申请上下文及有限有效期；已过期、撤销、消费或被后续申请替代的凭据不能完成切换。
3. 目标邮箱正式切换时仍必须满足**规范化全局唯一性**；不能因为邮件曾发送成功就忽略另一个账号抢先占用的竞合。
4. 正式生效一次性替换账号邮箱关系，不产生两个并存正式邮箱，也不改 Account ID、Player 身份或历史 Game 成绩。
5. Game Playing 时普通邮箱变更不能借此前的待决验证链接绕过 AUTH-16 的设置限制；正式提交前必须重新检查当前账号状态。必要的密码安全恢复不受此普通设置限制。

## 5. Session 生命周期和并发（AUTH-3 A、AUTH-6 A、AUTH-9 A、AUTH-12 A）

- 会话具有服务器权威的**有限空闲截止**与不可无限延长的**绝对最大寿命**。两者均必须有效且会话未撤销，才能认证；具体时长按公开可配置安全政策确定，不在此固定数字。
- 允许合法且受保护的续期；续期不能把原会话寿命延至最初绝对截止之后。超过绝对截止必须重新认证，建立新会话。
- **退出、密码成功重置、主动改密、合法撤销**立即使对应旧会话和原续期资格失效。续期与撤销竞合取服务器正式成立的权威次序：先续期后撤销仍最终失效，先撤销后续期则续期拒绝。
- 多设备各有独立会话寿命。一个设备续期不延长其他设备、不恢复被取代的旧游戏连接、不自动获取新的 Player 权限。
- 会话无效并不自动撤销 Room Member、Game Participant、Host、已提交 Replace 或已正式评分结果。客户端需重新登录及恢复原合法 Player；原 InitialReveal、Turn、Peek/Spy 绝对截止不暂停、不重置。
- 断线宽限只用于已确认的逻辑在线状态变化，不延长认证或私人结果的授权；不能把仍在宽限视为可用已撤销凭证。

## 6. 与 Room/Game 生命周期的结合（AUTH-16 修订版、AUTH-19、AUTH-15-Lobby A）

### 6.1 单账号单 Room / 回到当前游戏

- 账号已在 Room A：另一个标签页、设备直接访问 Room B / Create Room，不创建第二身份；提供回 Room A 的安全入口。
- 当前 Room 处于 Game Playing，访问普通设置或其他业务页面，应提示“正在游戏中”并提供回到**本人被授权的当前 Game**入口。进入游戏需校验认证 + Account–Player 关系；新连接按 CM-68 正式接管旧连接。
- 禁止通过直接业务接口绕过限制；**Playing 时普通账号设置**（展示名、邮箱、主动改密、注销等）拒绝，不等于阻断正常重新认证、合法密码安全恢复、强制撤销或合法原 Game 行动。
- Game Completed/Aborted 后，Playing 专属设置限制解除；但 Room 可能已返回 Lobby，**成员资格不因 Game 结束自动清除**，单 Room 规则继续生效。
- 安全恢复正式成功撤销旧会话时，原游戏继续按时钟运行，既有 Host/Player 身份不自动删除；只有重新合法认证并接管当前连接后才可恢复未过期的当前权限。

### 6.2 AUTH-15-Lobby A：自助注销前必须合法 Leave（最终确认）

1. 账号可以通过自助流程申请注销，但**仍拥有有效 Room Member 身份时不能直接提交/正式执行注销**。先独立完成 Room **Leave**，再单独发起注销；没有自动串接、没有跨域“全部一起成功”承诺。
2. **Lobby 普通成员**：合法 Member Leave 后不再占席；完成后可提出注销。
3. **Lobby Host 且有其他成员**：依 Phase 4 的 Host Leave 转移规则，合法转移给加入时间最早的剩余成员，并移除离开 Host；随后才可申请注销。
4. **Lobby Host 是唯一成员**：合法 Host Leave 导致 Room Closed；随后才可注销。
5. **Game Playing，包括 Host 与普通成员**：普通 Leave 禁止，普通账号注销禁止；不能因注销删除冻结 Game Participant、迁移 Host 或触发额外 Game Aborted。
6. **Game Completed / Aborted**：Room 如果回 Lobby，依然要先 Leave；Room Closed 或已正式移除成员时，不再占据现行 Room Member 资格，可在满足其他安全条件后申请注销。
7. **Leave 已正式成功，随后注销失败**：Leave 不回滚；原账号依然存在且其剩余有效认证资格按实际注销结局判断，可按当前状态重新操作。若注销正式成功，则撤销全部账号旧会话、停止新授权，并依适用隐私与保留政策处理账号关联信息。
8. **并发约束**：Leave 与另一设备的 Join/Create/注销竞争时，每次正式执行都重新核对当前账号是否属于 Room。账号注销正式提交时不得残存有效 Room Member；不能用旧 View 或同 ID 重试制造双 Room 或已注销后重新加入的状态。
9. **历史业务事实不变**：注销不删除或重分配 Game Participants 历史、已正式完成成绩、100 分重置、最终胜负及不可变 Command 结局。可在适用政策下删除或去标识化个人信息；历史终局访问仍受原 Participants 权限及保留期约束，不向已注销账号的新冒名者开放。

### 6.3 Lobby 与 Playing 判定原则

- 仅参加 Lobby 不自动禁止普通设置；但注销仍要求先 Leave。
- Playing 的普通设置限制按账号关联的当前有效 Game Participant 身份判断，而不是按该设备是否正显示游戏页面判断。
- Playing 期间服务器撤销会话、密码安全恢复、超时处理及 Game Aborted 仍依法生效；任何 UI 提示不能阻碍这些安全操作。

## 7. 注册名 / 展示名与秘密隔离（AUTH-18-R1、Phase 4）

- **注册名与游戏展示名是同一个账号属性**：注册时必填，正式创建 Account 及修改时均须在全部现行账号中全局唯一。名称可修改，但新名称在正式提交时必须再次满足唯一性，包含并发注册和并发改名。规范化/名称比较规则须统一、确定，并由 PostgreSQL 唯一约束提供最终保证；前端检查不能代替服务端约束。
- 名称**不是登录凭据或授权主体**；Account ID 与 Player ID 仍独立稳定。名称修改不得改变 Room Member、Game Participants、已成立 Command 或历史成绩。显示名唯一不意味着知道名称就有权操作。
- Game Playing 期间普通显示名修改由 AUTH-16 禁止。已结束 Game 的权威分数不因更名、注销或账号资料去标识化而重算。
- 公共视图不应包含密码、凭证、认证重置链接、邮箱验证凭据或隐藏牌数字。认证错误、日志、连接通知、前端 Mock 不得泄漏这些值。
- 私人结果读取需同时满足：**当前认证有效、Account–Player 绑定有效、当前 Game Connection 有效、原业务 Decision 与私人授权尚有效**。重连、重新登录、会话续期不会重启截止或恢复过期偷窥秘密。
- 已发出但在安全撤销后才被网络送达的数据无法被物理撤回；服务器不得在失去权限后再**新发送**私人结果。

## 7.1 注册邮箱验证码修订不变量（AUTH-I124～AUTH-I134）

以下条款是 AUTH-5-R1 的正式增量；与旧版“未验证即可正式注册并参与”冲突的旧条款不再适用。

- **AUTH-I124**：未验证邮箱控制权不得正式完成新账号注册。
- **AUTH-I125**：仅符合邮箱格式或发送验证码成功，不构成邮箱控制权证明。
- **AUTH-I126**：未完成验证的注册申请不得获得正式 Account、认证会话或 Room Member 身份。
- **AUTH-I127**：注册验证码绑定规范化邮箱、注册用途、注册上下文、有限有效期，且一次有效。
- **AUTH-I128**：错误、过期、消费、撤销、被替代的注册验证码不得完成注册。
- **AUTH-I129**：注册验证和账号创建的正式提交必须保持同规范化邮箱全局唯一，并发只能成立一个账号。
- **AUTH-I130**：注册成功的账号邮箱立即为 Verified；未完成注册不拥有可通过密码恢复的正式账号。
- **AUTH-I131**：注册验证码不得用于登录、密码重置、邮箱改绑或接管其他账号。
- **AUTH-I132**：发送、重发和校验验证码须由服务端限流、防滥用，并避免无权限信息泄漏。
- **AUTH-I133**：邮件发送失败、取消、超时或失败校验不得创建可登录正式账号。
- **AUTH-I134**：注册验证码不可出现在公开视图、日志或无需授权的响应中；前端 Mock 不得声称具有真实邮箱验证能力。

## 7.2 展示名唯一性修订不变量（AUTH-I135～AUTH-I142）

- **AUTH-I135**：注册名与游戏展示名为同一账号属性；注册时必须提供。
- **AUTH-I136**：所有现行正式账号的注册名/展示名按统一名称比较规则全局唯一。
- **AUTH-I137**：正式注册提交时，邮箱唯一性与注册名唯一性必须同时成立。
- **AUTH-I138**：名称允许修改，但必须在正式更名时重新验证唯一性，不能仅依赖查询预检查。
- **AUTH-I139**：并发注册与并发改名不能产生两个相同规范化名称的现行账号；约束冲突须安全处理。
- **AUTH-I140**：名称不是登录凭据，不得替代 Account ID、Player ID 或其他权限校验。
- **AUTH-I141**：更名不得改写 Room、Game、Player 身份、已经成立的 Command 或正式历史结算。
- **AUTH-I142**：Game Playing 期间，普通名称修改仍被 AUTH-16 禁止；不可用其他设备或直调接口绕过。

## 8. 生命周期竞合验收矩阵（契约级）

| 编号 | 前置情况 / 竞争 | 必须得到的唯一合法业务效果 |
|---|---|---|
| AUTH-T01 | 未登录 Create/Join Room | 拒绝；无 Room Member |
| AUTH-T02 | 未完成邮箱验证码验证即尝试注册完成、登录或 Join | 不创建可登录 Account；拒绝登录/Join；完成验证码校验与正式注册后才可登录 |
| AUTH-T03 | 两个注册申请验证同一规范化邮箱并发正式注册 | 最多一个 Verified Account 正式成立，不泄漏其他账户详情 |
| AUTH-T04 | 邮箱已被历史 Unverified 账号占用，真正邮箱持有人尝试注册 | 不接管或迁移 Account/Player；按 AUTH-10 授权争议处理标识，注册须保持唯一性 |
| AUTH-T05 | 未完成注册的用户忘记填写的密码，或历史 Unverified 账号请求恢复 | 未完成注册须重新安全开始注册；历史 Unverified 邮箱不得获得密码恢复权限 |
| AUTH-T06 | 注册验证码重复、过期、错误邮箱或被重发替代 | 不得完成正式注册，不得重复创建 Account 或越权验证其他邮箱 |
| AUTH-T07 | 修改邮箱期间 Game 正式 Start | Playing 阻止普通邮箱切换，保留原正式邮箱 |
| AUTH-T08 | 修改邮箱时新地址被抢注 | 不允许产生第二个邮箱占用；原正式关系保留 |
| AUTH-T09 | 改密与旧 Session 续期竞合 | 改密成功后全部旧会话无效；不得续期复活 |
| AUTH-T10 | 会话续期接近绝对寿命 | 不能越过原绝对截止，之后重新认证 |
| AUTH-T11 | 设备 A Logout，设备 B 仍合法登录 | 仅 A 失效；B 认证独立保留 |
| AUTH-T12 | 玩家游戏时账号会话到期 | Turn/能力时钟不暂停，需重认证，超时默认照旧 |
| AUTH-T13 | 手机接管电脑游戏连接 | 仅一个当前 Player 连接，历史 Accepted 不变，旧端不得获新秘密 |
| AUTH-T14 | 同账号在 Room A，异设备 Join Room B | 拒绝 B；可安全指向 A；不新建席位 |
| AUTH-T15 | 两设备同时 Create Room | 最多一个成功当前 Room Member；另一个不得占第二 Room |
| AUTH-T16 | Lobby 普通成员先 Leave 后注销 | 两个独立正式结果；注销失败不回滚 Leave |
| AUTH-T17 | Lobby Host 有继任者，申请注销 | 先 Host Leave 合法转移并移除；之后才可注销 |
| AUTH-T18 | Lobby 唯一 Host，申请注销 | 先 Host Leave→Room Closed；之后可注销 |
| AUTH-T19 | Host/普通成员 Game Playing 申请注销 | 拒绝普通注销及 Leave，Game 继续，角色不变 |
| AUTH-T20 | Game Completed/Aborted 后 Room 回 Lobby | 仍占 Room，先 Leave 后可注销 |
| AUTH-T21 | Leave 与跨设备 Join/注销竞争 | 服务器按正式顺序守护成员唯一性与注销权限 |
| AUTH-T22 | 成功注销后历史 Game 结果 | 比分/Winner 不改写；仅在适用隐私保留/授权边界内访问 |
| AUTH-T23 | 第二个账号使用已占用注册名注册，或将名称改为已被占用值 | 拒绝产生同名的现行账号；不泄漏不必要的账号信息 |
| AUTH-T24 | 安全通知送达失败或重复 | 原账号变更仍仅正式执行一次，无秘密泄漏 |
| AUTH-T25 | 正在 Playing 的攻击者滥用登录/恢复入口 | 防护不冻结游戏时钟，也不能阻断合法安全恢复 |
| AUTH-T26 | 会话失效后尝试读取过期 Spy | 必须拒绝，重新认证不能恢复旧秘密 |

| AUTH-T27 | 两个注册请求以同一规范化注册名并发提交 | 至多一个账号以该名称正式创建成功，邮箱验证步骤不能绕过名称唯一约束 |
| AUTH-T28 | 修改展示名与另一账号注册同名并发 | 至多一个正式提交成功；失败一方保留原名称及身份 |
| AUTH-T29 | Game Playing 时从另一设备提交改名 | 拒绝普通改名，Game/Player/Turn 状态不变 |

## 9. 前后端交接边界（不定义 API 或代码）

**后端必须独立保证**：账号认证/撤销、注册名/展示名全局唯一、Account–Player 与唯一 Room 归属、单 Game Connection、敏感操作再认证、邮箱状态/唯一性、绝对/空闲期限、并发正式裁决、过期私人结果拒绝及注销时 Room 空置校验。前端禁用按钮不能替代上述守卫。

**Codex 前端可安全并行实现**：注册名 + 邮箱 + 密码填写 → 发送注册验证码 → 输入验证码 → 正式注册成功/失败/重发提示、登录/邮箱验证状态、忘记密码（未验证限制与安全一致反馈）、Session 失效重新认证提示、单 Room 恢复/正在游戏中返回入口、Lobby Host/Ready/Leave、普通账号设置与 Playing 限制、独立改密/改邮箱/注销交互及安全通知提示、唯一名称的注册/更名冲突提示。所有未实现服务逻辑必须由契约一致的 Mock 适配层表达，不得伪造真实安全保障。

在后端授权前，不要凭 Mock 自行规定真实 HTTP/WebSocket 路由或 Token 格式；不应直接引入 OAuth、多因子认证、账号合并、好友、观战或额外 Game 规则。可配置运营值（会话时长、滥用阈值、邮件凭据有效期、争议审核流程）需满足本协议边界，并在实现验收前明确对外政策。

## 10. 冻结验收结论及非阻断事项

### 契约级审核

- **通过**：AUTH-1～AUTH-19（其中 AUTH-5 B 已由 AUTH-5-R1 注册必验邮箱验证码替代，AUTH-18 A 已由 AUTH-18-R1 全局唯一展示名替代；含 AUTH-16 修订版及 AUTH-15-Lobby A）、Account/Session/Player/Room/Connection 区分、跨 Room 并发唯一性、Lobby Leave 后注销、Game Playing 账号设置限制与安全恢复例外、历史 Game 结果不回写。
- **无已知仍需用户选择的阻断性业务分支**。AUTH-15-Lobby A 将先前 Lobby 注销时序歧义关闭。
- **认证契约已冻结并可作为 Phase 5 实现输入**；不代表真实注册登录、邮件、安全、并发、端到端或渗透测试已完成。

### 实施前需制定但不属于新业务决策

- 会话空闲/绝对寿命、注册验证码和恢复链接有效期、验证码长度/重发/错误次数及风控阈值等有限且可配置的运营参数；审计/申诉的具体流程及适用隐私数据保留期限。
- 展示与真实认证接口的交接形式、客户端 Mock 切换方式、无障碍 UX、错误码、测试环境邮件投递策略和服务端审计日志的脱敏设计。
- 账号注销后的业务记录可保留范围及个人关联信息去标识化方式需按适用隐私要求评估；不得作为无条件永久保留个人资料的借口。

### 冻结纪律

后续若涉及 Account–Player 归属、Room 唯一性、密码/邮箱恢复权、Playing 中的设置限制、历史资料或秘密权限的实质改变，应提出显式 AUTH 修订及影响范围，经确认后调整本文件和前后端契约，不得由前端或后端单方推定。
